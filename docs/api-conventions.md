# API conventions

Reference form of `plan.md` §7 for what exists through Phase 5.0 (clinical foundations).

- **Base path**: `/api`, URI versioning, default version `v1` → business routes are `/api/v1/<resource>`. Health is version-neutral: `/api/health`, `/api/health/ready`. Swagger UI: `/api/docs` (JSON: `/api/docs-json`), non-production only by default.
- **Unmatched routes** anywhere return the standard error (`ROUTE_NOT_FOUND`).
- **JSON**, `camelCase`, UUID ids, ISO-8601 UTC timestamps. Request bodies are limited to 1 MB.
- **Validation**: DTOs with `class-validator`/`class-transformer`. Global pipe: unknown properties are rejected (`UNKNOWN_FIELD`), types are never silently coerced (`@Type()` explicitly where needed). Failures return `VALIDATION_FAILED` with `details[]`.
- **Success shapes**: controllers return explicit `{ data }` / `{ data, meta }` (`src/common/dto/api-response.ts`). There is no global response-wrapping interceptor (ADR-0005).
- **Errors**: one shape for every failure, see [error-codes.md](error-codes.md). Services throw `DomainError(code)`; never put values (names, ids of people, query text) in error messages.
- **Contract**: [openapi.json](openapi.json) is the generated, committed OpenAPI document (regenerate with `npm run openapi:export`). It declares the `bearer` scheme, marks `@Public()` operations with `security: []`, and gives every 4xx/5xx response the `ErrorResponse` schema (all of this is applied by `finishOpenApiDocument`, `src/common/http/openapi.ts`; nullable fields need an explicit `type`, or a generated client types them as `object`); [frontend-integration.md](frontend-integration.md) explains how to use the API.
- **Request id**: every response has `X-Request-Id`. A client-sent `X-Request-Id` is honored only if it is a canonical UUID; otherwise a new one is generated. The same id appears in the error body and the logs.
- **Status codes**: 200/201/202/204 success; 400 validation or malformed; 401 not authenticated (`UNAUTHENTICATED`; `ACCESS_TOKEN_EXPIRED` tells the client to refresh; `INVALID_CREDENTIALS` for a failed login); 403 not permitted or tenant not usable (`FORBIDDEN`, `TENANT_*`); 404 not found (also used for other tenants' records); 409 conflict; 413/415 body problems; 422 business rule; 429 rate limited or account locked (`RATE_LIMITED`, with `Retry-After`); 500/503 server.
- **Authentication**: `Authorization: Bearer <access token>` for every non-public route; the refresh token lives only in the httpOnly `dt_refresh` cookie (see [authentication.md](authentication.md)). Tokens are never accepted from a query string. `/api/v1/auth/*`, `/api/v1/me*` and `/api/v1/patients*` responses are `Cache-Control: no-store`.
- **CORS**: exact-origin allow list from `CORS_ALLOWED_ORIGINS` (`CORS_ALLOW_CREDENTIALS=true` for the refresh cookie); allowed headers `Content-Type, Authorization, X-Request-Id, Idempotency-Key, X-Expected-Tenant-Id`; `X-Request-Id` and `Retry-After` are exposed to browsers.
- **Path parameters** are declared in the contract: every `{id}` of a path appears in the operation's `parameters` as a required string (`format: uuid` for ids). A contract test fails for an undeclared one; give a new params class `@ApiProperty({ format: 'uuid' })` next to `@IsUUID()`.
- **`X-Expected-Tenant-Id`** (optional request header, tenant-scoped routes only). The active clinic lives on the server session shared by every browser tab, so a tab that still shows Clinic A could write into Clinic B after another tab switched. A client that sends the clinic id it believes it is acting in gets `409 TENANT_MISMATCH` (nothing done) when it differs from the session's active clinic. Compared case-insensitively; an empty or malformed value is a mismatch, not "absent", so send the header only when the clinic is known. Ignored on public and no-clinic routes. Checked by `TenantGuard` after authentication and before any database lookup; the answer reveals neither id.
- **`Idempotency-Key`** (optional request header on routes marked `@IdempotentRoute()`: the `POST`s that create things, from sub-phase 5.1). Send a fresh UUID per user action and repeat it when retrying. A repeat with the same body runs once and replays the first answer (same status and body, for 24 hours); the same key with another body is `422 IDEMPOTENCY_KEY_REUSED`; while the first request is still running a retry is `409 IDEMPOTENCY_KEY_IN_USE` with `Retry-After`; a key that is not 1 to 255 printable ASCII characters is `400 IDEMPOTENCY_KEY_INVALID`. Keys are scoped to the signed-in user and clinic. **Only successful requests are remembered**: a request that failed is sent again with the same key and gets its real answer. See ADR-0016.
- **Optimistic locking** (`version`, from sub-phase 5.1): versioned resources (patients, appointments, encounters) carry an integer `version`; an update sends the version it read, and a stale one is `409 VERSION_CONFLICT` (reload, merge, send again; the error does not carry the current version). Backend helper: `updateWithVersion` (`src/common/versioning/`).

## Adding an endpoint (checklist)

1. Controller under `src/modules/<domain>/`, thin; logic in a service.
2. DTOs with `class-validator` + `@ApiProperty`; explicit response DTO/mapper (never return Prisma entities).
3. `@ApiTags`, documented success and error responses.
4. Throw `DomainError` for business rules; add new codes to `error-codes.ts` **and** `docs/error-codes.md`.
5. Add an e2e test, including error cases.
